1.2 Architecture: EncryptedSharedPreferences Wrapper
-----------------------------------------------------
Create: lib/core/security/encrypted_prefs.dart

Class: EncryptedPrefs
  - Wraps SharedPreferences with AES-256-GCM encryption
  - Encryption key stored in FlutterSecureStorage (KeyStore/Keychain)
  - Key derivation: PBKDF2 with device-specific salt
  - All read/write operations transparently encrypt/decrypt

  Methods:
    - static Future<EncryptedPrefs> initialize()
    - Future<void> writeString(String key, String value)
    - Future<String?> readString(String key)
    - Future<void> writeInt(String key, int value)
    - Future<int?> readInt(String key)
    - Future<void> writeBool(String key, bool value)
    - Future<bool?> readBool(String key)
    - Future<void> writeDouble(String key, double value)
    - Future<double?> readDouble(String key)
    - Future<void> remove(String key)
    - Future<void> clearAll()
    - Future<bool> verifyIntegrity() — HMAC check on stored data

1.3 Key Management Strategy
---------------------------
  - Master encryption key generated on FIRST app launch
  - Stored in FlutterSecureStorage (Android KeyStore / iOS Keychain)
  - Key never leaves secure hardware enclave
  - If key is lost (factory reset), data is unrecoverable (by design)
  - Key rotation: optional, on admin request via sync

1.4 Tamper Detection
--------------------
  - Each encrypted value includes an HMAC-SHA256 tag
  - On read: verify HMAC before decryption
  - If HMAC mismatch → data tampered → trigger security alert
  - Store integrity_hash of entire prefs blob in secure storage
  - On app launch: verify integrity_hash; if mismatch → lock app

1.5 Migration Strategy
----------------------
  - On first launch of v2.0.0:
    1. Read all existing plain SharedPreferences data
    2. Initialize EncryptedPrefs with new encryption key
    3. Re-write all data through encrypted wrapper
    4. Delete plain SharedPreferences
    5. Store migration_completed flag in secure storage
  - If migration fails → roll back, log error, retry on next launch

6.1 Sync Architecture
---------------------
  Design: Store-and-forward with conflict resolution

  Sync Queue Model:
    - Each local record has syncStatus: 0=pending, 1=synced, 2=conflict
    - SyncQueue manages pending operations
    - FIFO order, retry with exponential backoff
    - Max retries: 5, then mark as conflict

  Sync Triggers:
    - Manual: "Sync Now" button in dashboard
    - Automatic: When connectivity restored (listen via connectivity_plus)
    - Scheduled: Every 4 hours if online (background, if possible)
    - On app launch: If last sync > 24h ago and online

6.7 Sync Push/Pull Protocol

        {
          "entity_type": "receipt",
          "entity_id": "local_uuid",
          "operation": "create",
          "payload": { ... },
          "client_timestamp": "2026-05-04T14:30:00Z"
        },
        ...
      ]
    }

    Response:
    {
      "success": true,
      "sync_token": "new_sync_token",
      "results": [
        {
          "entity_id": "local_uuid",
          "server_id": "server_uuid",
          "status": "accepted",
          "conflict": false
        },
        ...
      ],
      "conflicts": [  // Only if any conflicts exist
        {
          "entity_type": "receipt",
          "entity_id": "local_uuid",
          "local_version": { ... },
          "server_version": { ... },
          "resolution_options": ["use_local", "use_server", "merge"]
        }
      ]
    }

  PULL (server → client):
    POST /api/v1/sync/pull
    Request:
    {
      "device_fingerprint": "sha256...",
      "user_id": "uuid",
      "sync_token": "last_sync_token"
    }

    Response:
    {
      "success": true,
      "sync_token": "new_sync_token",
      "updates": [
        {
          "entity_type": "receipt",
          "entity_id": "server_uuid",
          "operation": "update",  // create, update, delete
          "payload": { ... }
        },
        ...
      ],
      "security_config": {  // Optional: push security config updates
        "min_version_code": 3,
        "login_expiry_days": 21,
        "max_offline_days": 7,
        "force_sync": false
      }
    }

7.1 Device Fingerprinting
--------------------------
Create: lib/core/security/device_fingerprint_service.dart

Class: DeviceFingerprintService
  Methods:
    - static Future<String> generateFingerprint()
        * Combine multiple hardware identifiers:
          - Android ID
          - Board, Brand, Device, Hardware, Model, Product
          - Build fingerprint
          - Serial number (if available)
        * Add persistent UUID stored in FlutterSecureStorage
          (survives app reinstall, tied to KeyStore)

        * Return final fingerprint

    - static Future<String> getOrCreateFingerprint()
        * Return cached fingerprint if exists
        * Generate new one if first run

    - static Future<bool> isDeviceBound(String storedFingerprint)
        * Compare current fingerprint with stored fingerprint

        * Store in server record (when online)

  Key Design Decisions:

    - Emulator detection: flag emulators differently for testing
    - Root/jailbreak detection integrated (see 7.3)

7.2 Anti-Tamper: APK Sharing Prevention
-----------------------------------------
  Problem: User copies APK to another device

  Solutions (layered):
    A) Device Binding (primary):
       - On first login, bind account to device fingerprint
       - On subsequent launches, verify fingerprint matches
       - If mismatch → block access, show "Device mismatch" screen
       - Admin can reset binding via dashboard

    B) App Signature Verification (Android):
       - Verify app was signed with expected signing key
       - If APK was re-signed (pirated), signature won't match
       - Native code check (harder to bypass from Dart)

    C) Integrity Check:
       - Check for known tampering tools (Xposed, Frida)
       - Verify app is running in release mode (not debug)
       - Check for emulator signatures

  Implementation:
    Create: lib/core/security/app_integrity_service.dart

    Class: AppIntegrityService
      Methods:
        - static Future<bool> verifyAppSignature()
            * Android: Use PackageInfo to get signing certificate
            * Compare with known hash of production certificate
            * If mismatch → app was re-signed → block

        - static Future<bool> isRunningInDebug()
            * Check kDebugMode flag
            * Check for debugger attachment
            * If debug mode in production build → block

        - static Future<bool> isDeviceRooted()
            * Check for su binary
            * Check for known root management apps
            * Check for test-keys in build fingerprint
            * Use root_detection package

        - static Future<bool> isEmulator()
            * Check for emulator-specific build properties
            * Check for goldfish, generic, sdk in build info
            * Check for known emulator MAC addresses

        - static Future<SecurityReport> runFullCheck()
            * Run all checks
            * Return report with pass/fail for each
            * Calculate risk score
            * Log results for server review

7.3 Downgrade Prevention
-------------------------
  Problem: User installs older APK to bypass security fixes

  Implementation:
    Create: lib/core/security/version_service.dart

    Class: VersionService
      Methods:
        - static Future<bool> isDowngrade()
            * Get current versionCode from PackageInfo
            * Compare with stored min_version_code in FlutterSecureStorage
            * If current < stored → DOWNGRADE DETECTED

        - static Future<void> initializeVersion()
            * On first launch of a version:
              - Get current versionCode
              - If > stored min_version_code → update min_version_code
              - Store in secure storage (persists across reinstalls)

        - static Future<void> enforceVersion()
            * If downgrade detected → clear sensitive data, block app
            * Show full-screen blocking message

        - static Future<int> getCurrentVersionCode()
            * Return current app versionCode

        - static Future<String> getCurrentVersionName()
            * Return current version name (e.g., "2.0.0")

      Storage:
        - min_version_code stored in FlutterSecureStorage
        - Updated only when current version is HIGHER than stored
        - NEVER decreases (monotonically increasing)

      Native Android Enhancement:
        Create: android/app/src/main/kotlin/.../VersionProtection.kt

        - Store min_version_code in SharedPreferences with MODE_PRIVATE
        - Check in MainActivity.onCreate() BEFORE Flutter loads
        - If downgrade detected → launch blocked activity immediately
        - This prevents bypass by modifying Dart code

SECTION 11: SECURITY THREAT MODEL & MITIGATIONS
================================================================================

THREAT 1: APK copied to another device
  Mitigation: Device fingerprint binding on first login
  Residual Risk: Medium — Can be bypassed by copying secure storage

THREAT 2: APK decompiled and re-signed
  Mitigation: App signature verification in native code
  Residual Risk: Low — Requires extracting and matching signature

THREAT 3: Older APK installed to bypass security
  Mitigation: Monotonically increasing min_version_code in secure storage
  Residual Risk: Low — Requires clearing secure storage (which deletes data)

THREAT 4: SharedPreferences tampered (rooted device)
  Mitigation: HMAC integrity check on all encrypted values
  Residual Risk: Medium — Rooted devices can bypass client-side checks

THREAT 5: Device time changed to bypass expiry
  Mitigation: Server time validation on sync; detect time jumps
  Residual Risk: Low — Offline bypass possible but detected on next sync

THREAT 6: Factory reset → fingerprint changes
  Mitigation: Persistent UUID in KeyStore survives factory reset on most devices
  Residual Risk: Medium — Some devices clear KeyStore on factory reset

THREAT 7: Backup/restore to new device
  Mitigation: Fingerprint includes hardware-specific identifiers
  Residual Risk: Low — Hardware IDs won't match on different device

THREAT 8: Brute force login
  Mitigation: Login attempt tracking with lockout after 5 failures
  Residual Risk: Low — Lockout is time-based and enforced locally

THREAT 9: Offline data exfiltration
  Mitigation: All data encrypted with device-bound key
  Residual Risk: Low — Data is unreadable without the key

THREAT 10: Sync man-in-the-middle
  Mitigation: HTTPS only, token-based auth, payload integrity checks
  Residual Risk: Low — Standard TLS protections
